# Матрица трассировки требований

## 1. Назначение матрицы

Матрица трассировки показывает связь между критериями приёмки первой лабораторной работы, моделью данных и контрактом API.

Она позволяет проверить, что каждая основная функция системы имеет необходимые данные и соответствующий серверный метод.

## 2. Матрица требований

| ID | Требование | Сущности и поля | API | Критерий приёмки |
|---|---|---|---|---|
| REQ-01 | Создание заявки на оплату | `PaymentRequest`: `id`, `number`, `title`, `description`, `amount`, `counterpartyId`, `createdByUserId`, `status`, `createdAt` | `POST /api/payment-requests` | Менеджер создаёт заявку с корректными данными. Система сохраняет её со статусом `New` и уникальным номером |
| REQ-02 | Назначение исполнителя | `PaymentRequest`: `assigneeUserId`; `User`: `id`, `role` | `PATCH /api/payment-requests/{id}/assignee` | Руководитель отдела назначает директора. Исполнитель сохраняется, статус заявки остаётся `New` |
| REQ-03 | Перевод заявки в работу | `PaymentRequest`: `status`, `assigneeUserId` | `PATCH /api/payment-requests/{id}/status` | Назначенный директор переводит заявку из `New` в `InProgress`. Другой директор не может выполнить этот переход |
| REQ-04 | Просмотр списка заявок | `PaymentRequest`, `Counterparty`, `User` | `GET /api/payment-requests` | Авторизованный пользователь получает список заявок, доступных ему согласно его правам |
| REQ-05 | Просмотр одной заявки | `PaymentRequest` | `GET /api/payment-requests/{id}` | При существующем идентификаторе возвращаются данные заявки, при отсутствующем — `404 Not Found` |
| REQ-06 | Получение справочника контрагентов | `Counterparty`: `id`, `name` | `GET /api/counterparties` | Клиент получает список контрагентов для выбора при создании заявки |
| REQ-07 | Проверка допустимости действий | `User`: `role`; `PaymentRequest`: `status`, `assigneeUserId` | `PATCH /api/payment-requests/{id}/assignee`, `PATCH /api/payment-requests/{id}/status` | Пользователь не может выполнять операции, запрещённые его ролью или текущим состоянием заявки |

## 3. Связь с моделью данных

Для выполнения требования создания заявки используются поля таблицы `PaymentRequest`. Поле `counterpartyId` связывает заявку с контрагентом, а `createdByUserId` определяет её создателя.
Для назначения исполнителя используется поле `assigneeUserId`. Оно ссылается на пользователя с ролью директора.
Для перевода заявки в работу используется поле `status`. При этом сервер проверяет назначенного исполнителя и допустимость перехода из текущего статуса в новый.
Таким образом, модель данных содержит информацию, необходимую для реализации основных требований системы.

## 4. Связь с контрактом API

Каждой основной операции соответствует отдельный метод API:

- создание заявки — `POST /api/payment-requests`;
- назначение исполнителя — `PATCH /api/payment-requests/{id}/assignee`;
- изменение статуса — `PATCH /api/payment-requests/{id}/status`.

Назначение исполнителя и изменение статуса разделены на разные запросы. Это позволяет независимо проверять права пользователя и соблюдать бизнес-правила системы.

## 5. Проверка критериев приёмки

### Критерий 1. Создание заявки

**Предусловия:** пользователь авторизован и имеет роль менеджера. В справочнике существует выбранный контрагент.

**Действия:**
1. Менеджер вводит название, описание и сумму.
2. Менеджер выбирает контрагента.
3. Клиент отправляет запрос `POST /api/payment-requests`.

**Ожидаемый результат:** сервер создаёт заявку, назначает ей уникальные `id` и `number`, устанавливает статус `New` и сохраняет данные в PostgreSQL.

### Критерий 2. Назначение исполнителя

**Предусловия:** пользователь авторизован как руководитель отдела. Существует заявка со статусом `New` и пользователь с ролью директора.

**Действия:**
1. Руководитель отдела выбирает заявку.
2. Руководитель назначает директора.
3. Клиент отправляет запрос `PATCH /api/payment-requests/{id}/assignee`.

**Ожидаемый результат:** поле `assigneeUserId` содержит идентификатор выбранного директора, а статус заявки остаётся `New`.

### Критерий 3. Перевод заявки в работу

**Предусловия:** пользователь авторизован как директор и назначен исполнителем заявки со статусом `New`.

**Действия:**
1. Директор открывает назначенную ему заявку.
2. Директор выбирает действие «Взять в работу».
3. Клиент отправляет запрос `PATCH /api/payment-requests/{id}/status` со значением `InProgress`.

**Ожидаемый результат:** сервер проверяет назначение и права пользователя, сохраняет новый статус `InProgress` и возвращает успешный ответ.

Если запрос выполняет другой директор, сервер отклоняет операцию.

## 6. Вывод

Матрица трассировки связывает требования первой лабораторной работы с моделью данных и контрактом API. Для основных функций определены необходимые сущности, методы запросов и ожидаемые результаты проверки. Это позволяет использовать матрицу как основу для последующей реализации и тестирования системы.
